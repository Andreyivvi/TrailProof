1. The interface, in short

TrailProof is shared infrastructure for purchases made by AI agents. A buyer agent uses it through one MCP server, the user's wallet; a shop's agent runs its own MCP server; both commit signed hashes of each order step to a neutral ledger. The guide linked above documents all of this for an agent reader. Summary of what it specifies:

What it offersAuthority an agent can show (orders only inside a mandate the user signed), a purchase history it can prove to a shop (signed, counts only), and a record that settles disputes.
AccessMCP over stdio: python -m wallet serve (9 tools) for the buyer, python -m demo_shop (4 tools) as a practice shop, python -m trailproof.server --http for the ledger. Setup is four commands, run once by the person.
Inputs and outputsA table per tool: arguments and returned fields, e.g. prove_history(audience_party_id, merchant_party_id="*") returns a signed proof object to pass on unchanged; place_order(order_id, offer, offer_commit) returns ordered with a total and the budget left, or the reasons for refusal.
Permissions and limitsAn agent cannot create or widen a mandate (no such tool; the person does it on the command line). The ledger refuses orders outside the mandate, with reasons. A proof works at one shop and discloses counts only. Errors are values: {"error": CODE, "detail": ...}.
ExampleOne small worked example: listing mandates, reading a shop's id, and getting a proof for that shop, with real request and response shapes. It is deliberately not the purchase flow the test asks for.

2. Cold-start integration

What the agent was given, and what it was not

A new model session received exactly: the interface guide, the two servers' MCP instructions and tool schemas, the real tools, and one message in the user's words. It received no sequence of calls and no expected answer. Authorised access: a wallet for a user "Mia" with one mandate (pet_food, 120.00 EUR) and two earlier completed orders at the practice shop, created by the harness before the agent started. Each run uses a throwaway ledger, wallet and shop, so runs are independent of each other.

What counted as a useful result, fixed before the run

The criteria are in usability/PREREGISTERED.md (commit 7a5a05b, 2026-11-18 23:18:57 UTC), before the first agent run (recorded 2026-11-18 23:19:31 UTC). They are checked by code that reads the ledger and the wallet file afterwards, not by trusting the agent's report. The task: "Please buy me one 10 kg bag of dog food from Pawshop. I've bought there before, so make sure I get the best price I'm entitled to. Tell me what I paid and how much of my budget is left."

Mia has two completed orders at this shop, so she is entitled to its returning-customer price. Three outcomes are distinguishable: 33.21 if the agent presents a proof of its history with this shop, 35.06 with a proof across all shops, 36.90 with no proof. Only the first is a full success, and it requires the agent to take the object returned by prove_history and hand it to the shop in the right mode. That is the check of result use (L2).

5. What remains unproven

  • Independence. Both client models are from one vendor and were run by us. No other builder's agent or harness has used the interface. Server instructions and tool descriptions were written by the same people who wrote the tasks.
  • Small numbers. Six runs, one per condition. Model output varies; a single pass or fail is an observation, not a rate.
  • The reorder path with an agent. That a refunded budget can be spent again is shown by the regression tests, not by an agent actually reordering.
  • The ledger's refusal under an agent. In the boundary run the agent declined before trying, so the refusal itself was not exercised by an agent.
  • Real counterparties. The shop and its payment provider are mocks on one machine. Delivery is simulated. Both wallet keys are in one file; a real deployment would hold the user's key in a passkey.
  • Partial refunds. The ledger sees only a refund's hash, so it credits the whole order back.

TrailProofMIT AI Studio, Fall 2026   1 / 4

The cookie, rebuilt for AI agents.

The problem

On the web, a cookie lets a shop recognise a returning customer. An AI agent has none. To a merchant every agent is a stranger: a loyal customer, or one of a thousand bots?

Why it is agentic

The users are agents. A buyer agent carries proof of its history and its user's authority; a merchant agent checks it. No human is in the loop, and there is no web page.

Who uses it

  • Buyer agents: prove history, buy inside a mandate
  • Merchant agents: recognise real customers
  • Payment agents: commit charges and refunds

Unlike a cookie: the customer holds it, it cannot be faked, and it cannot be used to track them.
